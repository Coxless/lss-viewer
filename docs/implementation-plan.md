`concept.md` を実装するための計画です。マイルストーン（M0〜M6）は concept 10章を踏襲し、作業・順序・完了条件を具体化しています。

## 1. 仕様を調べて分かったこと

### 1.1 仕様どおりでは成立しない点（本計画で変更する）

| # | 問題 | 根拠 | 本計画の決定 |
|---|---|---|---|
| A | **初回転送量 1 MB が、shells と density だけで超える** | 6章の例で shells.bin = 18,402×24 + 97,638×4 = 832 KB、density.bin = 76×125×68 = 646 KB（非圧縮）。合計 1.48 MB | density.bin は初回に読まず、しきい値を最初に動かしたときに取得する。shells は頂点を 8 バイト（位置 int16×3、法線 oct 符号化 int8×2）に縮め、インデックスは差分符号化して gzip する |
| B | **「最初の表示」の定義が曖昧** | 自動モードの遠景は 40万×0.25 = 10万点 = 800 KB で、これだけで予算の大半を使う | 「最初の表示」＝ metadata、hierarchy、深さ1までのタイル（最大9ノード・295 KB）、shells の描画完了、と定義する。残りのタイルはその後に順次読み込む |
| C | **模擬カタログを「移植」できない** | プロトタイプには C のソースがなく、24 KB の Wasm バイナリのみ（`gen_mock` などをエクスポート）。ソースは現存しないことを確認済み | 同等のモデルを Rust で新規実装する。プロトタイプの Wasm を Node で実行して出力を取り出し、δ のヒストグラムと見た目で比較する。バイト一致は求めない |
| D | **M4 の完了条件と M5 が矛盾** | M4「プロトタイプの全操作を再現」には U5・U9 が含まれるが、実装は M5 | M4 の完了条件は U1〜U4、U6〜U8、U10 とする |
| E | **M2 では転送量の目標を判定できない** | shells と density は M3 で初めて生成される | M2 は点群分のみ判定し、全体の転送量は M3 で判定する |
| F | **事前計算とブラウザ再計算で輪郭がずれる** | shells.bin を量子化前の δ から作ると、U5 で量子化後の δ から作った輪郭と一致しない | CLI も `density.bin` と同じ量子化済み δ から shells を作る |
| G | **高密度レイヤーで δ=+3 の埋め値が等値面になる** | v1.1 の δ=+1〜+5 の範囲に +3 が入り、観測範囲の端に偽の面が出る | 範囲外は値ではなく専用のマスク（格納時は番兵値 255）で表す |

## 2. 全体の設計方針

マイルストーンをまたいで効く決定です。後から変えると手戻りが大きいので、最初に固定します。

1. **データ形式を契約にする。** M0 で `docs/format.md` を書き、`lss-viewer-core::format` に読み書きの両方を実装する。CLI・Wasm・テストはすべてこれを使う。ビューア側の TypeScript の読み取りは、Rust が生成した fixture で検証する。
2. **`DataSource` インターフェースを M2 で導入する。** `getHierarchy()`、`getTile(id)`、`getShells()`、`getDensity()` を定義し、HTTP 版とインメモリ版（U9 の CSV 用）を差し替えられるようにする。これで M5 でビューアを変更せずに済む。
3. **結果の決定性を保証する。** 乱数はシード固定の `rand_chacha` を使い、rayon の有無やネイティブ／Wasm の違いで出力が変わらないようにする（同一バイトになることをテストする）。これが画像比較テストの前提になる。
4. **並列処理は `parallel` feature の裏に置く。** GitHub Pages は COOP/COEP ヘッダーを設定できず SharedArrayBuffer を使えないため、Wasm は単一スレッドに固定する。
5. **部分取得するのは points.bin だけにする。** shells と density は `.bin.gz` として丸ごと取得し、Worker の `DecompressionStream` で展開する。ホストの圧縮設定に依存しない。
6. **Wasm は遅延読み込みにする。** 初回表示に Wasm は不要で、U5 と U9 を使うときに初めて読み込む。
7. **レイヤーを M3 から枠組みとして作る。** 最初から `metadata.layers` を正とし、UI の文言もレイヤー名から生成する。concept の `metadata.voids` はレイヤーと重複するので廃止する。
8. **処理中の座標は f64、配信形式で f32／int16。** 属性値は `kind<<12 | brightness`（bit 15 は 0）とする。プロトタイプの実装に合わせた定義で、int16 の正規化読み込みでも負にならない。

## 3. マイルストーン

規模は S／M／L の相対値です。依存関係は基本的に直列で、M4 と M5 は M3 の後なら並行できます。

```
M0 → M1 → M2 → M3 ─┬→ M4 ─┬→ M6
                   └→ M5 ─┘
```

### M0：土台（S）

- [x] 開発環境：Ubuntu Workshop の `dev`（定義は `.workshop/`）。Rust 1.99.1、`wasm32-unknown-unknown`、wasm-pack 0.15.1、binaryen（wasm-opt 120）、Node 24.22.2。ホストには Rust も Node も入れず、`workshop exec dev -- <コマンド>` または `workshop shell` で使う。Vite のポート転送と Playwright のブラウザは未設定で、必要になる M1・M2 で追加する
- [x] リポジトリを整える。コミットがまだ1つもなく、ブランチは `master`。`main` に揃えて concept とプロトタイプを最初のコミットにする
- [x] Cargo ワークスペースと Vite の雛形、`.gitignore`（データセットと SDSS の生データは入れない）
- [x] GitHub Actions：`cargo test`、`clippy`、wasm ビルド、web ビルド
- [x] **Wasm の検証**：`fast-surface-nets` と `cdshealpix` が `wasm32-unknown-unknown` でビルドできること、および `.wasm` のサイズを確認する。ここで駄目なら自前実装に切り替える
- [x] **Firefly の評価（半日で打ち切り）**。結果を `docs/decisions.md` に残す。判断基準は、ボイド輪郭の重ね表示・スライス・飛び込み・U5 を、自前実装より少ない変更で載せられるか、およびスマホ性能と初回転送量の目標を満たせるか
- [x] `docs/format.md`（concept 6章＋本計画の変更）
- [x] `cosmology.rs` と `mock.rs`。astropy の値を一度計算してテストに固定する（CI に astropy を入れない）

**完了条件**：`cargo test` が通る。模擬カタログ60万件を同一シードで同一バイトに出力できる。Firefly の判断が記録されている。

> Firefly を拡張する判断になった場合、M2 と M4 は作り直しになります。以降は自前ビューアを前提に書いています。

- [x] `catalog.rs`：列名の大文字小文字を無視した検出、`#Table1` のスキップ、z の範囲フィルタ、棄却件数のレポート
- [x] `octree.rs`：シャッフル＋安定振り分け、K=4096、最大深さ14

- [x] カメラ静止時に描画を止める、DPR の上限
- [x] 性能表示（U8）、`?bench=1`

**完了条件**：`?bench=1` で PC 60fps（100万点）、中位スマホ 30fps 以上（25万点）。点群部分の転送量が目標内。fps は実機での計測が必要（Playwright のソフトウェア描画では判定できない）。

### M3：密度場とボイド輪郭（L）

最も不確実性が高い段階です。concept の「偽の壁を作らない」要件はここに集中します。

- [x] `footprint.rs`：HEALPix Nside=128。件数が少ない入力では自動で Nside を下げる（穴だらけのマスクを防ぐ）
- [x] `density.rs`：CIC → n(r) → 正規化畳み込み → 量子化
- [x] `shells.rs`：`fast-surface-nets` で生成後、範囲外セルに接する頂点を含む三角形を除去して頂点を詰め直す。法線は正規化する。入力は `δ − しきい値`（高密度は符号を反転）
- [x] 8 バイト頂点、インデックスの差分符号化、gzip
- [x] `voids.rs`：簡易検出（極小点＋26方向の光線、端に当たる光線3本以上で棄却）
- [x] `metadata.layers` の生成、`lss-viewer-cli build` で全段を一括実行
- [x] ビューア：輪郭の描画（フレネル風の α）、レイヤー切り替え、自動モードの不透明度
- [x] SDSS 実データの取得（下記リスク R2 に注意）。取得 SQL と手順を `docs/` に残す
- [x] 単体テスト：一様な点で δ 平均が 0±0.02、一様場で面が出ない、球状の低密度領域で球面が出る
- [x] **追加テスト**：マスクに穴を開けた模擬データで、範囲外から1セル以内に輪郭の頂点がないこと（偽の壁の回帰テスト）

**完了条件**：テストが通る。全体の初回転送量が 1 MB 以下、4G 相当で2秒以内（Playwright のネットワーク制限で計測）。SDSS 実データで泡構造が見える（目視確認）。

## 4. リスク

| # | リスク | 確認したこと・兆候 | 対策 |
|---|---|---|---|
| R1 | **Range と gzip の組み合わせ** | GitHub Pages の HTML に `Accept-Encoding: gzip` 付きで Range を送ると、**圧縮後のバイト列の範囲**が 206 で返った。Fetch 仕様ではブラウザが Range 時に `identity` を付けるはずだが、`.bin` では未確認 | M1 で実ホスト確認。駄目なら `--split-files` に切り替える |
| R2 | **`TOP 300000` の偏り** | `ORDER BY` がない `TOP` は打ち切る行が不定で、空の一部が欠ける可能性がある（未確認）。SQL に明るさの列もなく、5.1 の属性が埋まらない | M3 で取得後に空のカバー範囲を図にして確認する。偏っていれば CasJobs で全件取得する。等級は `PhotoObj` と結合する |
| R3 | **VAST（DR7）と SDSS（DR18）の範囲のずれ** | カタログは NSA v1.0.1 ベースで、DR18 より範囲が狭い。DR18 にしかない領域にはボイドが表示されない | M6 で範囲外を明示する。宇宙論パラメータの差（Ωm 0.315 と 0.31）は z=0.1 で約 0.1 Mpc/h の見込みで無視する |
| R4 | **範囲外フィルタの見た目** | 三角形を落とすと輪郭に穴が開く。意図した動作だが、シルエットが不自然に見える可能性がある | M3 の早い段階で SDSS の範囲で目視する |
| R5 | **Wasm のサイズ** | Rust 版はプロトタイプ（24 KB）より大幅に増える見込み | 遅延読み込みで初回から外す。M0 で実測する |
| R6 | **スマホの fps** | 加算合成はオーバードローが重い | M2 で実機確認。不足なら DPR と点のサイズ上限を調整する |
| R7 | **広い z 範囲の CSV** | z=0.6 まであると r≈1538 Mpc/h で、格子間隔が約 25 Mpc/h に粗くなりボイドが解像できない | 格子数の上限の範囲で警告を出す |
